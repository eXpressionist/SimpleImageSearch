# OpenCart Image SQL Generator Design

## Goal

Add a separate module for OpenCart 3 that generates SQL for assigning main product images. The module is not part of the existing batch image search workflow. It helps match exported OpenCart products to manually named image files, then produces reviewable SQL for updating `oc_product.image`.

The module never applies SQL to OpenCart directly.

## Inputs

The first version is paste-first and does not require file uploads.

- Products text: one product per line, containing `product_id` and `sku`.
- Files text: one image filename per line.
- Image path prefix: a manually entered prefix applied to every selected filename.
- OpenRouter API key: entered in the frontend and stored only in browser storage.
- Matching settings: whether to use OpenRouter, selected model, and matching thresholds.
- Service word handling: whether to ignore common filename words during matching.

Recommended product input format:

```text
12345	ABC-001
12346	ABC-002
12347	ABC-003
```

Recommended files input format:

```text
ABC001.jpg
abc-002-main.webp
ABC_003.png
```

The product parser should accept tabs, semicolons, commas, and repeated spaces between `product_id` and `sku`.

## Output

The module returns:

- SQL statements for valid matches.
- A table showing `product_id`, `sku`, selected filename, final image path, matching method, and confidence.
- Products/SKUs without a matched file.
- Files not matched to any product.
- Parse errors.
- Conflicts or low-confidence matches.
- A saved history record for the run.

SQL format:

```sql
-- SKU: ABC-001, file: ABC001.jpg, method: normalized
UPDATE oc_product SET image = 'catalog/products/import/ABC001.jpg' WHERE product_id = 12345;
```

Only the standard OpenCart 3 `oc_product.image` field is updated. Additional product images in `oc_product_image` are out of scope.

## UI Design

Add a separate frontend section, tentatively named `OpenCart SQL`.

The page contains:

- Products textarea.
- Filenames textarea.
- Image path prefix input.
- OpenRouter API key input saved in `localStorage`.
- Toggle for using OpenRouter.
- Model selector with a lightweight default model.
- Action button: match and generate SQL.
- Results table.
- Copyable SQL block.
- Lists for unmatched products, unused files, parse errors, and conflicts.
- History list and detail view.

The API key is never sent while viewing history. It is sent only when generating a new match with OpenRouter enabled.

## Backend API

Add an isolated OpenCart module following the existing backend layering.

Endpoints:

- `POST /api/opencart/image-matches/generate`
- `GET /api/opencart/image-matches/history`
- `GET /api/opencart/image-matches/history/{id}`

The generate endpoint accepts the pasted product text, pasted file text, image prefix, matching settings, and optionally the OpenRouter key. It returns the match report, SQL, and saved `history_id`.

The backend is responsible for parsing, normalization, algorithmic matching, optional OpenRouter calls, response validation, SQL generation, and history persistence.

## Matching Flow

Matching runs in stages:

1. Parse product lines into `product_id` and `sku`.
2. Parse filenames into a clean list.
3. Normalize SKU and filenames for comparison:
   - lowercase;
   - remove file extension;
   - remove spaces, hyphens, underscores, and similar separators;
   - if enabled in settings, ignore common filename words such as `main`, `photo`, and `image`.
4. Find exact source matches.
5. Find exact normalized matches.
6. Find fuzzy matches with confidence scores.
7. If OpenRouter is enabled, send unresolved or uncertain cases to the selected model.
8. Validate all selected matches.
9. Generate SQL only from valid one-to-one matches.

Rules:

- One SKU can receive only one file.
- One file can be assigned to only one SKU.
- SQL is generated by `product_id`, not by SKU.
- Low-confidence matches are reported clearly.
- Invalid or conflicting LLM results are rejected or marked as conflicts.
- Ignoring service words is enabled by default, but the setting is saved in history so the run can be reproduced.

## OpenRouter Integration

Use architecture option 2:

- The frontend stores the API key in browser `localStorage`.
- On generation, the frontend sends the key to the backend only for that request.
- The backend calls OpenRouter and validates the model response.
- The backend does not save or log the key.

The model should be asked to return structured JSON with product IDs, SKUs, filenames, confidence values, and short reasons. Backend validation must check that every referenced product and file exists in the original input.

## History

History is stored in the backend database.

Each run stores:

- created timestamp;
- original product text;
- original file text;
- image prefix;
- matching settings;
- whether OpenRouter was used;
- model name;
- match results;
- generated SQL;
- unmatched products;
- unused files;
- parse errors;
- conflicts and low-confidence cases.

History does not store:

- OpenRouter API key;
- raw OpenRouter request or response bodies.

A single history table with JSON fields is acceptable for the first version because the module is report-oriented and does not need relational querying over individual matches.

## Testing

Backend tests should cover:

- product text parsing;
- filename parsing;
- normalization;
- exact matching;
- normalized matching;
- fuzzy matching;
- one-to-one validation;
- SQL escaping and generation;
- history creation and retrieval;
- OpenRouter response validation with mocked API responses.

Frontend verification should include:

- build;
- lint;
- manual flow through the new page;
- API key persistence in browser storage;
- history detail view.

## Security

The module must avoid leaking secrets:

- Do not save OpenRouter keys in the backend database.
- Do not include keys in logs.
- Do not return keys in API responses.
- Escape SQL string values for generated image paths.
- Treat generated SQL as text output only; do not execute it.
